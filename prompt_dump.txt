WHAT STAMPEDE DOES

A buyer of inference capacity brings usage data, their own prompts, constraints in plain English and real quotes they have received. Stampede answers four questions with their data, live:
1. Can a cheaper model do my work? Real model calls on my prompts, a sequential Bayesian test shown live, and cost per acceptable task from measured tokens.
2. What is this quote really worth? Parity-adjusted discount, net of expected deflation, prepay financing, shutdown exposure and resale value, with an expected saving and its uncertainty.
3. What should I buy? Sizing, a reservation price per model and tenor (the discount below which not to sign), a plan that respects my constraints, and an RFQ I can send.
4. How do I get out? If I must sell on day t, or a successor model launches, what do I recover?

Fast versus slow is the architecture. Model calls are slow and cost money, so they happen once per run (the parity stage). Everything else is fast math on stored posteriors, forecast residuals and fixed random draws, so every what-if recomputes in about a second without new model calls.

A small provider-side view (Phase 5) shows the utilization uplift band for a seller's own capacity and demand parameters.

Cut from the demo: precomputed JSON as demo data, static fan charts, stress-scenario cards, the five-mechanism benchmark (stays in eval.py), any multi-turn evaluator, any feature that cannot change when the user changes an input.

STAGES AND MATH

Write docs/live_math.md while building: for each stage, the formulas, units and every simplification, plus the hand-computed fixtures the tests use.

ingest (stages/ingest.py)
1. Deterministic parse with the v1 parser wrapped by the parity normalizing wrapper. Report method=deterministic and the invariant checks.
2. If the deterministic parse fails or fails invariants, and a key exists, the LLM fallback proposes a column mapping and unit conversions as JSON (schema-validated). The mapping is applied by deterministic code, never by letting the LLM emit data rows. Invariants (all must pass or the result is rejected): dates parse and are increasing after sorting with duplicate rate below 5%; tokens non-negative; the total after mapping is within 1% of an independent re-aggregation using the mapping; at least 14 distinct days. On rejection the user gets a precise error, never a best guess. Report method=llm_mapped and show the mapping for the user to confirm.
3. Numbers-only input (monthly tokens, growth, volatility) produces a synthetic daily series by the stated log-linear model, labelled USER_INPUT-derived and SIMULATED in its series provenance.

forecast
Reuse copilot.forecast with the session RandomDraws. Output P10, P50, P90 daily Series over the horizon (30, 60 or 90 days, user selectable) and stored residuals for what-ifs. Planned changes from notes use the v1 plan extractor, which keeps its substring-evidence rule.

workload and parity (stages/workload.py, parity_live.py, judge_adjust.py)
Mode:
- checked: checks supplied for all prompts. Each model response scores the fraction of checks passed (0 to 1).
- judged: otherwise.
Candidates and incumbent come from the catalog. Incumbent outputs are generated once per prompt and reused across candidates. Order prompts by a seeded shuffle.
Per-prompt outcome Y for candidate j versus incumbent i:
- checked mode: Y = 1 iff score_j >= score_i - margin (margin 0 by default, user may set up to 0.1).
- judged mode: both orderings, eligible judges are from families different from both models, two judges when available, verdict mean over (judge, ordering) in {+1, 0, -1}, Y = 0 iff mean <= -0.5. Judge prompts reuse parity.substitution.judge with rubric chosen by a short LLM archetype classifier whose output is shown to the user, who may override it. If no eligible judge exists for a pair, that pair is SKIPPED with the reason.
Sequential test per pair: Beta(1,1) on the observed rate pi. Batches of 4 prompts, minimum 8, cap at min(prompts, config cap). Stop with parity if P(theta >= THETA0) >= 0.95, no_parity if <= 0.05, otherwise undecided at the cap. THETA0 comes from config and may be overridden by the user between 0.80 and 0.99.
Judge-error adjustment (judged mode only): sample sens and spec from their Beta posteriors (artifact from Phase 0). Transform pi draws: theta = (pi + spec - 1) / (sens + spec - 1), clipped to [0,1]. Stopping rules operate on the adjusted posterior (Monte Carlo, 4000 draws each batch). If J < 0.5, no parity decision may be issued and the notice says why. Always report the raw and adjusted theta. Add the standing notice that judge error rates are assumed to transfer.
Effective cost per acceptable task (measured, not estimated from list tokens):
- tau_m = mean total tokens per task for model m on the user's prompts, with in and out tokens separately from provider-reported usage.
- c_m = on-demand cost per task = price_in_m * tokens_in_m + price_out_m * tokens_out_m.
- q_m: checked mode, mean score of model m. Judged mode, q_incumbent = 1 by definition (the incumbent is the quality reference) and q_candidate = adjusted theta mean. State this difference in the output notices.
- E_m = c_m / q_m. Break-even discount d*_m = 1 - E_inc / E_m (may be negative). Bootstrap over prompts for intervals.
Streaming: after every batch emit progress with n, successes, posterior mean and interval, P(parity) and cumulative cost. Emit an evidence event for each judged or scored prompt (indices only, no content). Pairs run in parallel across candidates, sequential within a pair.
Store posteriors in the session so downstream stages and what-ifs never re-call models.

quotes (stages/quotes_parse.py, quotes_rank.py)
Quote schema: provider, model_id, list_price_in_per_mtok, list_price_out_per_mtok (user-supplied or from the catalog), discount_pct, tenor_days, size_tokens, prepay_pct, start_in_days, resale_allowed, resale_fee_pct, conversion in {none, par_to_successor, best_in_class}, notes.
Email parsing: the LLM returns JSON where every populated field has a verbatim evidence_quote. A field is dropped (set to null, flagged) if the quote does not occur in the source text after whitespace normalization. Numbers in values must appear in the quote (after unit normalization). Missing fields are reported, not defaulted.
Blended price: K_list_m = blend of in and out prices using the measured in/out token mix on the workload, else the usage CSV mix, else the user-supplied input_output_ratio (ASSUMED if the user accepted the UI default).
Strike per token K_m = (1 - discount) * K_list_m.
Economics, per quote m, using these definitions (document derivation and every simplification in docs/live_math.md, and test with hand-computed fixtures):
- Reserve token consumption is limited by the task-equivalent demand: the buyer's incumbent token demand u_t converts to tasks via tau_inc, and the reserve on m can serve at most tasks_t * tau_m tokens per day.
- Avoided spend per consumed reserve token on m = E_inc * q_m / tau_m. If m is the incumbent, q = 1 and this equals the incumbent's blended on-demand price.
- Net saving per consumed token before financing and obsolescence = avoided spend - K_m.
- Parity-adjusted discount vs current spend = 1 - K_m * tau_m / (E_inc * q_m).
- Net of deflation = parity-adjusted discount minus the expected-deflation component D_m (from parity.valuation.discount over the consumption profile).
- Prepay financing: pi paid at t0, remainder pro rata over the tenor, discounted at buyer rate r_b (config, ASSUMED unless the user sets it).
- Expected resale and obsolescence: use the LSM valuation with the model's price chain, shutdown and notice dates from the obsolescence simulator (params_source carried through), resale fee, market depth scenario, and conversion clause mapped to the conversion fraction c (best_in_class and par_to_successor map to c=1 with the successor serving-cost ratio from config, ASSUMED). The price chain of the incumbent and of m are independent draws unless same provider and slot; state this.
- Output per quote: headline discount, parity-adjusted discount, net of deflation (each as Quantity), expected net saving in dollars with P10 and P90, probability that saving is positive, probability of deprecation notice before expiry, expected recovery on early exit, and a ranked order by expected saving minus rho times its SD (rho is the user's risk-aversion setting, default 0.25).
- Quotes on models not in the catalog get price-only metrics, a "parity not measured" notice, and are ranked in a separate group.
- Reservation prices: for every (model in catalog, tenor in {30, 60, 90}) show the minimum discount at which the expected risk-adjusted saving is zero (d_min from Module 3), so users know what to refuse even before they have quotes. When the seller-side bound d_max is shown, label it ASSUMED with its scenario.

valuation_live, sizing_live, exit_route
- valuation_live wraps parity.valuation (LSM, d_min, Shapley on demand) with the session draws. Default live path counts: 4000 training and 4000 evaluation paths. refine uses 20000 each. The out-of-sample evaluation set is always independent of the training set.
- Sizing Q* (sizing_live.py): newsvendor where the overage cost is Co = K_m - salvage (salvage = expected recovery from exit_route at the expected idle time, a Quantity SIMULATED) and the underage cost is Cu = on-demand avoided cost minus K_m. Critical ratio Cu / (Cu + Co) quantile of the forecast demand over the tenor. Compare against P90-peak and v1 sizing on the same inputs and show the expected-cost difference with intervals from the forecast draws (that is a diagnostic, not a claim of superiority).
- exit_route: for a contract held at day t0 with remaining share r, evaluate expected recovery of remaining value if sold on day t under (a) same_model_only matching and (b) substitution-aware matching, using parity.market with the benchmark substitutability matrix as true parity (MEASURED_BENCHMARK) and the synthetic buyer pool (SIMULATED). Overrides: sell day, remaining share, depth scenario, successor launch day, price cut size. Report the recovery distribution (P10, P50, P90) for both mechanisms and the spread. The standing notice states that the pool is synthetic.

WHAT-IF ENGINE (whatif.py)
- A session creates one RandomDraws object (normals, uniforms, Poisson counts, with sizes for the live and the refine path counts) from the session seed on first use. Every recompute reuses it (common random numbers).
- Override schema (pydantic, all optional): successor_launch_day, price_cut_pct, depth in {thin, normal, deep}, risk_aversion, conversion_fraction, growth_multiplier, plan_change_probability, excluded_providers, discount_overrides per quote id, quote edits, theta0, horizon_days, sell_day, remaining_share. Overrides that would require new model calls (changing candidates or incumbent, workload) are rejected with a message to start a new run.
- The recompute DAG: only stages downstream of the changed inputs run. Parity posteriors, evidence and the session cache are never touched.
- Deterministic guarantee: a what-if with no overrides reproduces the base run result exactly, and a what-if with overrides equals a from-scratch run with the same inputs and draws exactly. Both are gates.
- Latency target: p95 of what-if recompute at the live path counts at most 2.0 seconds on the development machine (record CPU model in the report). The response always includes recompute_ms.

PLAN, CONSTRAINTS, RFQ, NARRATIVE, AGENT

Constraints (constraints_parse.py): structured schema: excluded_providers, allowed_models, max_spend_usd, min_parity (value, applies to all or to a named archetype), min_tenor_days, max_tenor_days, max_prepay_pct, require_resale, require_conversion, max_provider_share, start_by_days. The LLM returns JSON where every constraint has a verbatim evidence_quote that must occur in the source text. Failing constraints are dropped and listed in the unparsed remainder. The user confirms the structured form before any run uses it. Hard versus soft: anything phrased as must, never, cannot, at most is hard (the parser tags it, the user can flip it).

Planner (planner.py, deterministic): options are stay-on-demand, switch-model-on-demand (only when parity decision is parity for the constrained threshold), and each parsed quote at sizes in {25, 50, 75, 100 percent of quote size, capped by Q* }. Choose the portfolio maximizing expected saving minus rho times SD subject to hard constraints (use scipy.optimize.milp). Output the plan, the options it rejected with the binding constraint for each, the comparison versus on-demand and the sizing Q*. With no quotes, the plan is the sizing plus reservation prices and an RFQ.

RFQ (rfq.py): a pydantic RFQ built from the plan: workload mix and measured tokens per task, acceptable models with minimum parity and measured parity, tenor, quantity range, maximum strike per token from the reservation price, resale clause required, conversion clause required, delivery profile from the forecast, evaluation criteria. The email text is rendered by the LLM only from the structured RFQ and passes the grounding guard, otherwise a deterministic template renders it with its label.

Narrative (narrative.py): the executive summary is written by the LLM when a key exists, otherwise templated. Every numeric token must bind to a Quantity id from the run through parity.agent.grounding (2 percent relative tolerance, no whitelist of small integers or round numbers). On failure: one repair attempt, then fall back to the templated narrative with the label. Return bindings {span, quantity_id}.

Agent (agent_live.py): an LLM tool loop through the gateway. Maximum 12 tool calls and a token cap. Tools are read-only over the session run: get_forecast, get_parity, rank_quotes, value_contract (evaluates a plan or quote variant using fast stages with the session draws), run_planner, build_rfq, simulate_exit. It decides the order of tools, explains trade-offs, and writes the narrative and RFQ email through the guard. It never selects numbers: every number it states comes from a tool result id. Stream each step as agent_step events (tool, arguments, a short result summary, quantity ids). If the agent fails or no key exists, the planner output stands, labelled "planner output, no LLM". Never present planner output as agent output.
